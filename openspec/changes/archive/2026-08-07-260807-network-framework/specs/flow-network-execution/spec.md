## Purpose

以 Kotlin 数据流向调用方连续报告网络执行状态、数据和失败，使业务能够组合处理、绑定协程生命周期并可靠地取消不再需要的工作。

## ADDED Requirements

### Requirement: 请求以类型安全的事件流执行
系统 SHALL 为每个请求返回冷数据流；只有在调用方收集时才开始执行。数据流 SHALL 以类型化事件区分开始、传输进度、成功数据、服务端事件、失败和取消，并且每次收集产生独立执行。

#### Scenario: 未收集的数据流不发送请求
- **WHEN** 调用方创建请求事件流但未开始收集
- **THEN** 系统不创建网络调用且不发送任何数据

#### Scenario: 收集成功请求事件流
- **WHEN** 调用方收集一个成功完成的请求
- **THEN** 事件流先报告开始状态，再报告一次成功数据并正常结束

### Requirement: 取消传播至所有执行阶段
系统 MUST 在收集协程取消、调用方显式取消或中间件终止时停止尚未开始的后续阶段，并将取消传播到正在进行的底层传输、文件读写和 SSE 连接。取消 MUST 不被转换为成功或普通业务失败。

#### Scenario: 取消正在下载的请求
- **WHEN** 调用方在下载仍在传输时取消收集协程
- **THEN** 系统关闭底层传输与文件资源，停止后续进度事件，并以取消终态结束

#### Scenario: 取消等待中的鉴权请求
- **WHEN** 请求正在等待中间件完成令牌刷新且调用方取消请求
- **THEN** 系统不发送该请求并释放等待相关资源

### Requirement: 错误具有稳定分类和原始原因
系统 SHALL 将配置、连接、超时、协议、编码、HTTP 状态、业务转换、文件和取消错误映射为稳定的错误类别，同时保留原始异常、请求关联标识及可安全展示的说明。敏感请求头和载荷不得出现在默认错误文本中。

#### Scenario: 服务器返回非成功状态
- **WHEN** 服务端返回非成功 HTTP 状态
- **THEN** 事件流产生包含状态码和可用错误载荷的协议错误，且不产生成功数据

### Requirement: 事件流可组合且资源边界明确
系统 SHALL 生成符合 Kotlin Flow 语义的事件流，以便调用方使用标准转换、过滤、合并和生命周期作用域操作符。无论完成、失败还是取消，系统 MUST 恰好释放一次网络调用、响应体和文件句柄。

#### Scenario: 调用方过滤进度事件
- **WHEN** 调用方使用标准 Flow 操作符过滤传输进度事件
- **THEN** 剩余事件的顺序与原始执行顺序一致且资源仍在终态时释放
